# Forms

jasy does both halves of the PDF form story: it **creates** fillable fields as ordinary layout
elements, and it **reads and fills** a form that came from somewhere else - a government PDF, a
supplier's order sheet - without touching the rest of the file.

## Creating fields

A field is a layout element like any other. It reserves a box and emits a widget annotation, so it
sits in a `Column`, paginates, and takes the same sizing props as a `Box`.

```ts
import {
  Document, Page, Column, Row, Text,
  TextField, Checkbox, RadioGroup, Dropdown, ListBox, PushButton, SignatureField,
  renderToBytes,
} from "@jasy/pdf";

Document([
  Page({ size: "A4", margin: 48, gap: 12 }, [
    Text("Registration", { size: 20, bold: true }),

    TextField({ name: "fullName", width: 260, height: 22 }),
    TextField({ name: "notes", width: 260, height: 60, multiline: true, maxLength: 500 }),

    Checkbox({ name: "agree", label: "I agree to the terms" }),
    RadioGroup({ name: "plan", gap: 8 }, [
      { value: "basic", label: "Basic" },
      { value: "pro", label: "Pro" },
    ]),
    Dropdown({ name: "country", width: 120, height: 22 }, ["DE", "AT", "CH"]),
    ListBox({ name: "topics", width: 160, height: 48 }, ["invoices", "reports"]),

    PushButton({ name: "reset", label: "Reset", action: "reset", width: 80, height: 24 }),
    SignatureField({ name: "signature", width: 200, height: 48 }),
  ]),
]);
```

Seven kinds: `TextField`, `Checkbox`, `Radio` / `RadioGroup`, `Dropdown` (alias `Select`), `ListBox`,
`PushButton` and `SignatureField`. The ones that offer a choice take it as the second argument, the
way `Column` takes its children - a radio choice as `{ value, label }`, a dropdown or list entry as a
plain string.

A `PushButton` does one of three things: `action: "reset"` clears the form, `{ open: url }` follows a
link, `{ submit: url }` posts the values - the last one Acrobat only, since neither poppler nor pdf.js
implements `/SubmitForm`.

jasy **bakes an appearance** for every field, so the value is visible before a reader redraws it. Opt
out with `renderToBytes(doc, { fieldAppearances: false })` if you would rather the viewer draw
everything. Field text is deliberately unkerned: viewers do not kern field text, and a baked
appearance has to match what the viewer will redraw over it.

## Filling a form somebody else made

The reader lives behind its own entry point, so a project that only ever generates PDFs never bundles
it:

```ts
import { readAcroForm, fillForm, flattenForm, PdfDocument } from "@jasy/pdf/edit";

// What is in there? Each field comes back with its name, type, current value, options and flags.
const form = readAcroForm(await PdfDocument.open(bytes));
form.fields.map((f) => `${f.name} (${f.type})`); // ["fullName (Tx)", "agree (Btn)", ...]

const { bytes: filled, warnings } = await fillForm(bytes, {
  fullName: "Ada Lovelace",
  agree: true,
  country: "DE",
});
```

Both `fillForm` and `flattenForm` return a **result object** - `bytes` plus what was touched
(`filled`, `flattened`) and any `warnings` - rather than raw bytes, so nothing about the operation is
lost on the way back.

You pass **values**, not object mutations. The form is a contract, and every way of breaking it is a
named error rather than a silent no-op: an unknown field name, a value of the wrong type for the kind,
a string past the field's `MaxLen`, a choice that is not in the list, a read-only field, a signature
field, a push button.

### Flattening

`flattenForm` stamps each field's appearance onto the page and removes the widget, so the values can
no longer be edited. `fillForm(bytes, values, { flatten: true })` does both in one pass:

```ts
const { bytes: frozen } = await fillForm(bytes, { fullName: "Ada" }, { flatten: true });

// or on its own, optionally for named fields only
const { bytes: partly } = await flattenForm(filled, { fields: ["fullName"] });
```

### The original file stays a prefix

Saving is an **incremental update**: the original bytes are kept verbatim, the changed objects are
appended, and the new cross-reference table chains back with `/Prev`. That gives a property you can
check with a diff - **the file you passed in is a literal prefix of the file you get back**. Nothing
was rewritten behind your back, and any signature over the original bytes still covers them.

An encrypted PDF works too: `fillForm(bytes, values, { password })` decrypts, fills and re-encrypts,
including the strings it carries over.

### Reading is broad, writing is narrow

jasy **opens** AES-256 (R6, R5), AES-128 (R4) and RC4 (R2/R3), because those files exist and you may
have to fill one. It **writes** only AES-256 R6 - the newest standard. Handing someone protection that
is known to be broken is not a feature, so the legacy handler refuses to encrypt.

Worth knowing when you compare: PDFKit and react-pdf both default to **40-bit RC4** when you ask them
for a password, and neither can emit R6 at all.

## The bug this design came from

A filled field showed nothing until you clicked it. The obvious story - "the viewer redraws lazily" -
was wrong, and a second implementation proved it: react-pdf's filled file behaved fine. The difference
was that theirs carried **no** appearance, so the viewer had to draw, while ours carried a **stale**
one from creation. We had written a new value and left the old picture behind: a self-contradicting
document.

So on fill, a text or choice field's appearance is **dropped**; a button's is kept, because its
appearance holds its on and off states and only the selector moves.
